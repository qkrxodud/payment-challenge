# 12장 측정 (./gradlew operationsMeasurement — 기본 check 와 knownFailingTest 에서 빠짐). 실행 환경은 environment.md. 측정 코드: PgOutageMeasurement(방식마다 하위 클래스),
# DailyReconciliationMeasurement. 같은 코드로 두 번 실행했다(2026-11-22, 연달아). 방식마다 실행 한 번에 한 번씩.
# 가. 카드사 장애: 카드사가 승인 요청을 받고 30초 동안 답하지 않다가 아무것도 남기지 않는다(LOST). PG 시간 제한은 운영 값(연결 1초·읽기 5초), 차단기도 운영 값
#     (최근 20번 중 50%, 최소 10번, 30초). 고객 20명이 장애 15초 동안 쉬지 않고 새 결제를 준비하고 승인을 요청한다(앞 답을 받으면 바로 다음). 15초 뒤 새 요청을 멈추고
#     보낸 요청이 끝날 때까지 기다린다. 응답 ms: 승인 요청 하나가 답(실패 포함)을 받기까지. DB 연결: 결제 서버 연결 풀(10개)의 쓰는 중인 연결을 5ms 마다 읽은 최대·평균.
#     결과 모름: 이 측정이 만든 결제 가운데 APPROVAL_UNKNOWN 으로 남은 수. 카드사가 받은 승인 요청: Mock PG 가 센 승인 요청 수.
# 나. 대사: 우리 결제 N건(오늘 인증한 승인 결제, JDBC 로 한꺼번에)과 카드사 결제 N건(승인)을 새로 만들고 1%를 카드사에서만 전액 취소한 뒤(알림 끔) 대사를 한 번 부른다.
#     걸린 ms: 대사를 부른 때부터 끝날 때까지. 카드사 거래 조회: 쪽(5000건) 수. 카드사 결제 조회: 뒤처진 결제를 따라가거나(운영) 결제마다(비교) 부른 수.
# 읽는 법:
#   - 시간 제한만: 모든 승인이 읽기 시간 제한 5초를 기다리고(중앙 5036~5040ms) 보낸 60건이 모두 결과 모름. 다시 시도: 한 요청이 15초(세 번 × 5초), 결과 모름 20건,
#     카드사는 승인 요청을 60번 받았다(같은 결제에 세 번). 차단기: 처음 보낸 20건(고객 수 — 최소 10번이 차기 전에 이미 보낸 요청)만 결과 모름이고 나머지는 승인 요청 없이
#     바로 실패(중앙 33ms). 카드사가 받은 승인 요청 20.
#   - DB 연결: 카드사 답을 기다리는 동안 연결을 쥐지 않는다(2장 — 승인 요청은 트랜잭션 밖). 시간 제한만·다시 시도의 평균 0.05~0.17개는 요청 앞뒤의 짧은 기록뿐이다.
#     최대 10/10 은 세 방식 모두 고객 20명이 같은 때 준비·인증 기록을 남긴 순간이다(카드사를 기다리며 쥔 연결이 아니다). 차단기의 평균 약 7개는 바로 실패한 고객이 쉬지 않고
#     다음 결제를 준비·기록해 초당 약 240건을 DB 에 쓴 결과다(이 측정의 고객은 답을 받자마자 다시 보낸다 — 실제 고객의 재시도 간격은 재지 않았다).
#   - 대사: 운영은 1천 건 306~434ms, 1만 건 995~1033ms(거래 조회 3번 — 1만 건 + 취소 100건). 결제마다 조회는 1천 건 4783~4984ms, 1만 건 35263~36130ms(조회 1만 번).
#     두 방식 모두 카드사에서만 취소된 결제를 모두 맞췄다(10건·100건).
# 두 실행에서 다른 것: 응답·대사 시간이 같은 범위 안에서 조금씩 달랐고, 차단기의 승인 요청 수(3710 / 3643)가 달랐다. 결과 모름·카드사 승인 요청·맞춘 결제 수는 같았다.
# 처음 실행은 측정 코드의 주문번호가 64자를 넘어 준비가 모두 실패해(승인 요청 0) 고치고 다시 돌렸다(아래에 없음).
