# 8장 재고 측정 (./gradlew stockMeasurement). 결정 3의 재고 저장소(와 변경 번호 비교는 승인 서비스)만 구현마다 바꿈.
# 재고 100개 상품 하나에 주문 300건(상품 1개씩, 10000원, 쿠폰·포인트 없음)을 미리 준비해 두고, 승인 요청 300건을 스레드 300개에서 래치로 한꺼번에 보낸다.
# 겹침을 고정하지 않는다. 카드사(Mock PG)는 바로 답한다. 결제 서버의 DB 연결은 HikariCP 기본 10개다. 묶음마다 3번(#1~#3), 묶음 전에 재고 5·주문 20 묶음을 한 번 돌려 버린다.
#   승인: 답이 APPROVED 인 요청 수. 과판매: 승인 − 처음 재고(0 보다 작으면 0). 남은 재고: 묶음 뒤 stock.quantity, 괄호는 처음 재고 − 승인(같아야 맞음).
#   카드사 승인: Mock PG 가 승인한 건수 합. 답: 답별 개수(결제 상태 또는 오류 코드). 응답 ms: 요청마다 승인 서비스가 답할 때까지(중앙, p95, 최대).
#   전체: 래치를 연 때부터 300건이 모두 답할 때까지. 처리량: 300 / 전체(초) — 재고가 떨어진 뒤의 OUT_OF_STOCK 은 카드사를 부르지 않아 빠르게 끝나므로,
#   잠그지 않음(300건 모두 카드사 승인·승인 기록까지 감)과는 같은 일을 한 처리량이 아니다.
#   다시 시도: 변경 번호가 어긋나 인증 트랜잭션을 처음부터 다시 한 횟수(묶음 300건의 합, 한 건 최대 30번).
# 두 번 실행했다. 실행 환경은 environment.md.
